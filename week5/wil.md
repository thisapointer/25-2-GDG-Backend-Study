## 1. 객체지향이란?
    객체 지향 프로그래밍(OOP, Object Oriented Programming)
    - 컴퓨터 프로그램을 여러 독립적인 부품들의 조합, 즉 객체들의 상호작용으로 파악하고자 하는 컴퓨터 프로그래밍의 패러다임  


### 객체 지향의 특징
* **추상화**: 복잡한 대상의 핵심적인 속성과 기능만을 간추려 모델링하고, 불필요한 세부 사항을 숨겨 단순화하는 것
* **캡슐화**: 서로 연관있는 속성과 기능들을 하나의 캡슐로 만들어 데이터를 외부로부터 보호하는 것
* **상속**: 기존 클래스의 속성과 기능을 새로운 클래스가 물려받아 재사용 하는 것
* **다형성**: 어떤 객체의 속성이나 기능이 상황에 따라 여러 형태를 가질 수 있는 성질  
-> 어떤 역할에 대해 여러 가지 구현 방식이 존재할 수 있는 것  

<br>

클라이언트가 알아야 하는 것: 대상의 역할  
클라이언트가 알 필요 없는 것: 내부 동작 방식  
구현 대상의 내부 구조나 그 자체가 바뀌어도 영향을 받지 않음

<br>

#### 백엔드 개발자의 입장
데이터 저장소 / 주문 금액 할인 정책 / 회원 포인트 적립 제도 등등  
-> 여러 종류가 존재하고 무엇을 선택할지 논의 중,  또는 추후에 바뀔 수 있는 상황이라면?  
--> 역할을 만들어놓고, 그 역할을 수행하는 구현체를 바꿔끼자

    인터페이스: 클래스가 구현해야 하는 메소드의 집합, 클래스의 틀

## 2. SOLID 원칙
    좋은 객체 지향 설계를 위한 5가치 규칙

> 1. **SRP(Single Responsibility Principle)**: 단일 책임 원칙  
하나의 클래스는 단 한 개의 책임을 가져야 함  
> 2. **OCP(Open/Closed Principle)**: 개방-폐쇄 원칙  
클래스는 확장에 열려있어야 하며, 수정에는 닫혀있어야 함  
> 3. **LSP(Liskov Substitution Principle) 리스코프 치환 원칙**  
자식 클래스는 언제나 부모 클래스를 대체할 수 있어야 함  
-> 기능 변경X, 행동적인 호환성
> 4. **ISP(Interface Segregation Principle)**: 인터페이스 분리 원칙  
인터페이스를 각각 사용에 맞게끔 잘게 분리해야 함  
-> 하나의 큰 인터페이스보다 여러 개의 작은 인터페이스로 분리
> 5. **DIP(Dependency Inversion Principle)**: 의존관계 역전 원칙  
구체화가 아니라 추상화에 의존해야 함  
-> 구현 클래스가 아닌 인터페이스에 의존

다형성 만으로는 SOLID 원칙을 지킬 수 없기 때문에  
스프링은 의존성 주입(Dependency Injection)을 지원한다

*무작정 SOLID 원칙을 적용시키는 것보다 확장 가능성을 생각하여 구조를 만드는 것이 좋다

## 3. IoC(Inversion of Control)
    제어의 역전  
    - 객체 생성 및 관리에 대한 제어권을 개발자가 아닌 스프링 프레임워크가 대신 가져가는 것  
    - 스프링에서는 객체를 생성하고, 관리하는 역할을 스프링 컨테이너가 수행함  
    -> 스프링 컨테이너 = IoC 컨테이너

### 싱글톤 컨테이너
    객체를 딱 1개만 생성해서 필요할 때마다 재사용할 수 있게 하는 것
    - 스프링 기본 적용
    - 매번 객체를 생성하는 것이 아니라, 생성해둔 객체를 사용하므로 메모리 사용 효율적

<br>

> `ApplicationContext`: 스프링 컨테이너 인터페이스

> `Assertions`: AssertJ라는 테스트 전용 라이브러리의 api  

* `Assertions.assertThat(applicationContext.getBeanDefinitionNames()).contains("myBean")`  
-> 가져온 빈 중에서 myBean이라는 이름의 빈이 있다면 테스트 통과  
* `Assertions.assertThat(myBean1).isSameAs(myBean2)`  
-> 두 객체가 완전히 같을 때(속성값X, 주소O) 테스트 통과

#### 의존성 주입 방법
* 생성자 주입
    1. final 선언
    2. 생성자에 `@Autowired` 사용
        + 필요한 의존 객체의 타입에 해당되는 Bean을 찾아 주입함  
        (생성자가 하나라면 생략 가능)  
    
    <br>

    이 과정을 단축한 것이 `@RequiredArgsConstructor`
* 필드 주입
    1. final을 쓰지 않고 선언
    2. 필드에 바로 `@Autowired` 사용

    -> 의존성 변경 가능성, 테스트 용이하지 않음, 의존 관계 파악이 힘들어 권장하지 않음
* 수정자 주입 (세터 주입)
    1. final을 쓰지 않고 선언
    2. setter에 `@Autowired` 사용  
    3. setter를 통해 의존성 주입  
    
    -> 변경 가능성이 있는 의존 관계에 사용


### 조회되는 빈이 두 개 이상일 때(Annotation)
> `@Qualifier(이름표)`  
> -빈에 추가 이름표를 붙여, 여러 개의 빈 중에서 특정 이름표를 가진 빈을 사용하겠다고 명시  
> `@Primary`  
> -이 어노테이션이 붙은 빈을 먼저 선택하게 함
